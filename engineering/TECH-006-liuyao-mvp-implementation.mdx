# TECH-006 Liuyao MVP Implementation Specification

## Goal
Build the first Daily Mirror experience.

## Flow
Question → Liuyao Tool (Casting + Calculation + Traditional Analysis) → KNOWLEDGE-003 → KNOWLEDGE-004 Reflection Mapping → Mirror Runtime → Shiguang Persona → Memory Save.

## MVP
- Question input
- Three coin interaction
- Hexagram generation
- Knowledge retrieval
- Reflection output
- Memory storage

## Runtime Contract

The existing Liuyao Tool remains the only implementation and API entry. It accepts six bottom-up three-coin tosses plus optional explicit `analysisContext`. It deterministically returns line values, moving lines, original/changed hexagrams, palace, Shi/Ying, Najia, Six Relations, Five Elements, Six Spirits, void branches, useful-god selection, strength, generation/control relationships, hidden/flying spirit, timing candidates and rule evidence. The standalone Python prototype has been absorbed into the existing TypeScript tool and removed; no `v2` tool or duplicate endpoint exists.

`analysisContext` contains `topic`, `monthBranch`, `dayStem` and `dayBranch`. Topic begins as a user-selected broad hint and is resolved into an `intentSelection` by deterministic rules, with a strict-schema LLM fallback only for unclear language. The model returns real-world semantics, never a useful god; code maps the confirmed role and goal into traditional targets. Calendrical values are added deterministically at casting completion. If required context is absent, the Tool returns a complete casting/structure result and `analysis.status = context_required`; downstream layers must not fabricate missing analysis.

Knowledge Retrieval resolves the corresponding KNOWLEDGE-003 entries after computation and before the Reflection Runtime. It contributes classical text and meanings only; it neither recalculates nor mutates Tool facts. Traditional interpretation remains separate from Shiguang reflection.

The enhanced contract returns `classical`, `symbolic`, `reflectionMapping`, exact `movingLines`, and a deterministic `readingRule`. The classical branch contains complete judgment, Great Image, line text and Small Image data. The Reflection Runtime cannot supply missing classical content.

The Shiguang Persona contract returns six structured fields:

- Shiguang Sees
- Hexagram Meaning
- Mirror Understanding
- Practical Guidance
- Reflection Question
- Shareable Reflection

Runtime input is:

```text
User Question
+ Liuyao Tool divination / structure / analysis / evidence
+ KNOWLEDGE-003 classical text and meanings
+ KNOWLEDGE-004 supported reflection mappings
+ visible Personal Memory
```

The Reflection prompt labels Tool analysis as immutable computed facts. It forbids recalculation, completion, contradiction or replacement. `context_required` is preserved as an absence of a traditional conclusion, not an invitation for the LLM to improvise one.

`assembleMirrorRuntimeContext` is the only LLM context assembly path. Reflection mappings contain provenance and confidence; they are candidates for compassionate translation, never facts about the user.

## API Contract

`POST /api/v1/tools/liuyao/calculate` keeps its existing path. Request bodies remain backward compatible:

```json
{
  "tosses": [[2,3,3],[3,2,2],[2,2,2],[3,3,2],[2,3,2],[3,2,3]],
  "analysisContext": {
    "topic": "career",
    "monthBranch": "wei",
    "dayStem": "wu",
    "dayBranch": "shen"
  }
}
```

The response keeps `hexagram` for current clients; that object contains `divination`, `structure`, `analysis` and `evidence`. `knowledge` remains the separate KNOWLEDGE-003 retrieval result, while `reflectionKnowledge` is the separate KNOWLEDGE-004 bridge. Reflection drafts bind the same analysis context and recalculate structure, analysis and reflection mapping during save, preventing LLM or client tampering.

Draft v5 contains the answer-first response contract and `explanationTrace`. On explicit save it is persisted to `reflection_events.explanation_trace`; v1-v4 tokens remain readable. The owner-scoped trace endpoint is `GET /api/v1/daily-mirror/reflections/:id/explanation-trace`.

Personal Memory is optional evidence. The prompt forbids converting tentative inference into a user fact and requires the Insight to explain why the supplied symbol may relate to the present question rather than forecast the future.

The provider must answer the user's actual concern before offering reflection. `traditionalJudgment` starts with “先说结论 / 先说结果” and gives the bounded direction; `reasoningExplanation` cites only supplied Tool and Knowledge evidence; `shiguangInterpretation` translates it into conversational language afterward. Phrases that redefine the user's question or claim that reflection matters more than an answer are rejected by prompt and evaluation tests. The UI's primary completion path goes from practical advice directly to save; `reflectionQuestion` is a secondary optional branch.

Existing Reflection Memory columns remain unchanged. The processor maps `traditionalJudgment` to observation, `reasoningExplanation + shiguangInterpretation` to insight, and `practicalGuidance` to action suggestion. Previous six-field and legacy four-field Reflection Events are normalized during retrieval and lazy Memory processing, so no database migration is required.

Generated drafts remain unpersisted until explicit user save. A signed, short-lived draft token binds the generated reflection to its authenticated owner. Saving creates one `reflection_events` record and the PHASE-003 processor derives Event and Reflection Memory. Pattern Memory still requires repeated independent evidence.
