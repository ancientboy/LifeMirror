# PHASE-020 — 恋爱互动入口与可扩展关系引擎开发计划

> 本文档以 GitHub `main@7d7c1b7` 的现有实现为基线。目标不是推翻 LifeMirror 已完成的首页、每日指引、人物镜像、记忆与现实回访，而是把“看懂 TA、知道怎么回”建设为所有用户长期常驻的核心入口，并把当前“通用关系模板”升级为可逐步扩展到恋爱、朋友、同事、领导和家庭的关系引擎。新用户与长期用户只区分首屏信息密度和可用上下文，不区分是否拥有关系入口。

## 1. 产品结论

### 1.1 市场入口

第一阶段对外只打一个高频、立即有结果的场景：

> **看不懂 TA，也不知道怎么回？把聊天告诉拾光。**

首批只覆盖：

1. TA 这句话是什么意思；
2. 我现在怎么回；
3. 我要不要主动。

“恋爱”是获客入口，不是底层边界。底层继续建设统一的现实关系系统。

### 1.2 长期产品结构

```text
前台：恋爱互动的一个具体问题
  ↓
拾光：判断信号 + 可直接发送的回复
  ↓
用户：带回 TA 的真实回应
  ↓
系统：校准同一人物、同一关系和下一次建议
  ↓
扩展：朋友 / 同事 / 领导 / 家庭
```

### 1.3 不采用的方案

- 不创建五个互相独立的 Agent。
- 不要求新用户进入前先创建人物档案。
- 不要求首次使用前填写关系阶段、目标和长表单。
- 不把恋爱互动设计成只在首次访问出现、使用一次后下沉或消失的 onboarding。
- 不删除长期用户已有的今日指引、人物镜像、现实回访和周度内容；这些内容在常驻关系入口之后按上下文完整呈现。
- 不把模型生成内容写成 TA 的人格事实。
- 不把原始聊天截图长期写入 D1。
- 不因加入图片输入而替换现有 DeepSeek / Groq 文本主备链路。

## 3. 用户流程

## 3.1 所有用户长期常驻的核心入口

“看懂 TA、知道怎么回”不是新用户 onboarding，而是首页长期存在的主工作区。无论用户是否聊过、是否已经建立人物、是否已有今日内容，首屏都必须保留：

```text
看不懂 TA，也不知道怎么回？
[粘贴聊天、描述发生了什么或上传截图]

TA 这句话什么意思
我现在怎么回
我要不要主动
```

用户使用一次后，该入口不得消失、降级为探索页入口或移动到今日／周度内容之后。

所有用户共用同一个 `RelationshipWorkspace`、同一个 Composer、同一个关系引擎和同一套现实反馈闭环。用户状态只改变：

- 首屏说明文字的多少；
- 是否展示最近人物与未完成事件；
- 是否自动带入同一 TA 的上下文；
- 入口之后展示多少今日、周度和人物内容。

## 3.2 首访用户：更少内容，更多引导

真正无个人资料、无历史、无人物、无现实事件和无用户聊天的首访用户，首页第一屏只突出关系入口：

```text
看不懂 TA，也不知道怎么回？
把聊天发给拾光。它会先判断现在发生了什么，
再给你一句真正说得出口的话。

[粘贴聊天或描述发生了什么]
[上传聊天截图]

TA 这句话什么意思
我现在怎么回
我要不要主动
```

首次提交后直接给出结果，不要求先选人物或关系。首访状态下暂不在第一屏堆叠今日指引、周度镜像、人物管理和玩法解释。

## 3.3 回访但尚未建立人物

用户聊过但尚未保存 TA 时，仍显示同一个大入口，不改成轻量链接：

```text
今天想聊谁？
把最近的聊天、截图或发生的事情告诉拾光。

[继续上次的问题]
[输入或上传截图]
```

若上次案例仍未结束，可以显示“继续上次”；不能因为用户已经使用过一次，就把核心入口移动到页面底部。

## 3.4 已有 TA 或未完成事件

已有私密人物或待回复事件时，关系工作区在首屏增加人物和连续性：

```text
正在聊：小林 ▾

上次：你准备发出那条回复
[TA 后来回复了] [继续分析] [换一个人]

[粘贴新聊天、描述新情况或上传截图]
```

规则：

- 有明确未完成 case 时，可默认关联对应 TA，但人物选择必须可见且可切换；
- 有多个最近人物时，展示最近人物快捷项，不自动把新内容写入错误人物；
- 用户可选择“新的人”或“本次不关联人物”；
- 不要求用户重新讲述系统已经保存并确认过的背景；
- 现实反馈直接进入同一个关系工作区，不另造一套回访流程。

## 3.5 长期用户的完整首页

长期用户不是继续使用旧首页，而是在同一个常驻关系入口之后获得更完整的内容。建议顺序：

1. 常驻关系工作区；
2. 当前 TA 的待回复／待回访事件；
3. 今日指引或今日运势；
4. 最近人物与关系轨迹；
5. 周度镜像；
6. 塔罗、六爻、命盘、星盘等补充入口。

当待回访事件属于当前 TA 时，优先融合进关系工作区，避免首页出现两个相互竞争的输入入口。

## 3.6 拾光结果

默认结果包含四项，但不使用生硬标题堆砌：

1. 当前互动更可能发生了什么；
2. 哪些信息仍不能确定，最容易误判什么；
3. 一句可以直接发送的回复；
4. 接下来应该观察的现实信号。

结果底部提供：

- 复制回复；
- 换一种语气；
- TA 后来回复了；
- 以后继续聊这个人。

## 3.7 人物与关系确认

人物关系不在开始前强制选择。

```text
有明确表达：
“我男朋友最近……” → 自动识别 partner，不询问

已有明确未完成事件：
默认关联对应 TA，同时显示可切换的人物选择

信息不足但不影响建议：
“TA 不回我了” → 先给低假设建议，结果后轻量确认

信息不足且会明显改变建议：
“这句话怎么回” → 只问一次：
[暧昧中] [伴侣] [前任] [朋友/其他]
```

用户获得第一次价值后才出现：

> 以后还想继续聊这个人吗？给 TA 一个只有你看得见的称呼。

用户可以：

- 关联已有 TA；
- 新建私密人物；
- 本次不保存。

## 4.2 Composer 规则

- 文本上限从 300 提升到 2,000 字；
- 支持粘贴多轮对话；
- Enter 发送、Shift+Enter 换行保持不变；
- 附件按钮位于输入框左侧；
- 图片和文字可同时提交；
- 图片上传过程中不阻塞文字编辑；
- 发送前可删除、重新排序和补充“右边是我”等说明；
- 生成过程中继续支持停止；
- 失败后保留图片缩略图与输入，不要求重新选择。

## 4.3 截图规格

首版约束：

- JPG、PNG、WebP；
- 最多 3 张；
- 单张压缩后不超过 1.2 MB；
- 总体积不超过 3 MB；
- 长边压缩至不超过 1,600 px；
- 浏览器端移除 EXIF；
- 图片顺序即聊天顺序；
- GIF、HEIC、PDF 暂不支持，前端给出明确提示。

如果后续真实数据证明大量用户需要长对话，再增加 4–8 张分批识别，不在首版扩大请求风险。

## 4.4 常驻关系工作区与内容密度

新增 feature flag：

```text
NEXT_PUBLIC_RELATIONSHIP_ENTRY_ENABLED=true
```

该开关控制关系工作区是否启用，不用于判断用户是否有资格看到入口。开启后，所有用户首屏都渲染同一个组件：

```tsx
<RelationshipWorkspace
  mode={isNewHomeExperience(snapshot) ? "first_visit" : "continuing"}
  recentPeople={recentPeople}
  activeCase={activeCase}
/>

{!isNewHomeExperience(snapshot) && priorityFollowups}
{!isNewHomeExperience(snapshot) && dailyCard}
{!isNewHomeExperience(snapshot) && weeklyMirror}
```

禁止使用以下结构：

```tsx
if (flag && isNewHomeExperience(snapshot)) {
  return <RelationshipEntry />;
}

return <ExistingShiguangHome />;
```

`isNewHomeExperience` 只决定：

- 是否显示完整的新手说明；
- 是否展示示例场景；
- 是否暂时隐藏今日与周度内容；
- 是否展示最近人物和待回访事件。

它不得决定核心关系入口是否存在。

首页模式建议内部细分为：

```ts
type RelationshipHomeMode =
  | "first_visit"
  | "returning_unlinked"
  | "relationship_active"
  | "multi_relationship";
```

这些模式共用同一个输入、附件、流式响应和关系引擎，只改变首屏上下文与辅助内容。灰度失败时关闭 flag 即可回到当前首页，无需回滚数据库。

```ts
export type RelationshipDomain =

  | "client"
  | "parent"

  | "relative"
  | "other";

export type RelationshipStage =
  | "unknown"
  | "new"
  | "developing"
  | "stable"
  | "conflict"
  | "cooling"
  | "separated"
  | "repairing";

  | "roughly_equal"
  | "user_lower_power"
  | "user_higher_power"
```

继续保留：

```ts
relationshipLabel: string; // 用户自己的说法，例如“学姐”“孩子爸爸”
```

标准字段用于内部路由，自由标签用于自然展示。

## 5.2 分类结果

```ts
type RelationshipClassification = {
  domain: RelationshipDomain;
  role: RelationshipRole;
  stage: RelationshipStage;
  powerPosition: PowerPosition;
  personCandidates: Array<{ personId: string; score: number }>;
  goal:
    | "interpret_signal"
    | "draft_reply"
    | "decide_initiation"
    | "repair"
    | "set_boundary"
    | "refuse"
    | "prepare_conversation"
    | "other";
  confidence: number;
  missingCriticalField?: "role" | "speaker" | "goal";
  reasonCodes: string[];
};
```

`confidence` 仅用于系统决策，不向用户展示“置信度 73%”。

## 5.3 何时询问

只有同时满足以下条件才询问：

1. 缺失字段会导致明显不同的建议；
2. 无法从当前文字、图片和已有人物中稳定判断；
3. 只需一个短问题即可解决。

安全相关场景不受“一问上限”限制，例如未成年人、暴力、胁迫、自伤或职业高风险。

## 6.3 一个拾光，多套策略

保持一个 Shiguang Runtime。策略包只改变：

- 需要优先检查的信号；
- 对行动建议的风险权重；
- 允许和禁止的建议；
- 建议回复的语气与结构；
- 现实反馈要观察的指标。

| 策略 | 优先判断 | 必须避免 |
| --- | --- | --- |
| dating / romance | 投入是否对等、信号是否一致、是否适合主动 | 读心、操控、反复试探 |
| partner | 冲突核心、修复意愿、长期重复模式 | 只给话术，不处理重复伤害 |
| friendship | 互惠、误会或疏远、边界失衡 | 把普通疏远判成背叛 |
| colleague | 责任、协作、信息留痕、边界 | 把工作问题完全情绪化 |
| manager | 权力差、证据、时机、替代方案 | 鼓励情绪化对抗或冲动越级 |
| family | 长期角色、现实依赖、边界可执行性 | 用一句话术假装解决多年模式 |

首个 release 只把 `dating`、`partner`、`ex` 做到 production-ready；其他策略先使用安全 fallback，不宣传完整支持。

## 6.4 结构化响应

模型先返回可校验 JSON，再由前端自然展示：

```ts
type RelationshipAnswer = {
  classification: RelationshipClassification;
  judgment: {
    summary: string;
    facts: string[];
    hypotheses: string[];
    uncertainty: string[];
  };
  replyOptions: Array<{
    id: string;
    tone: "natural" | "warm" | "direct" | "boundary";
    text: string;
    why: string;
  }>;
  recommendedReplyId?: string;
  nextSignals: string[];
  clarification?: {
    field: "role" | "speaker" | "goal";
    question: string;
    options: Array<{ value: string; label: string }>;
  };
  safety?: {
    level: "normal" | "caution" | "urgent";
    reasonCodes: string[];
  };
};
```

校验失败时走一次修复；仍失败则使用文本 fallback，不向用户暴露 JSON 或模型参数。

## 7. 图片理解

## 7.1 Provider 设计

ChatGPT 支持图片理解不等于 LifeMirror 当前生产模型自动支持图片。视觉链路单独配置：

```text
VISION_PROVIDER=openai
VISION_BASE_URL=https://api.openai.com/v1
VISION_API_KEY=...
VISION_MODEL=<支持图片输入的模型>
VISION_MAX_TOTAL_BYTES=3145728
VISION_RETENTION_MODE=ephemeral
```

现有：

```text
DeepSeek → 普通文本主模型
Groq → 文本备用模型
```

保持不变。视觉模型只做截图解析，解析出的结构化对话再交给关系引擎。

## 7.2 提取结果

```ts
type ExtractedConversation = {
  pages: Array<{
    attachmentId: string;
    order: number;
    messages: Array<{
      speaker: "user" | "other" | "unknown";
      text: string;
      visibleTime?: string;
      signals?: string[];
      uncertain?: boolean;
    }>;
  }>;
  inferredUserSide: "left" | "right" | "mixed" | "unknown";
  missingRegions: string[];
  warnings: string[];
};
```

视觉模型只描述画面中可见内容，不推断 TA 的真实动机。关系判断在后续策略层完成。

## 7.3 图片隐私

- 原图仅存在于本次内存请求；
- 不写入 D1；
- 不写入日志、错误上报、产品指标或模型 trace；
- 服务端日志只记录附件数量、字节数、耗时和错误码；
- D1 只记录不可逆哈希、MIME、尺寸、解析状态和删除时间；
- 用户删除本次案例时，相关附件元数据一并删除；
- 前端明确提示“原图不会保存，识别后的事件由你确认后才会进入人物记录”。

## 10. 旧数据兼容与迁移

当前 `privatePeople`、`relationshipLoops`、`lifeEventLoops` 仍可能存在于 `account_data.settings_json` 和本地快照中。

迁移分四步：

### M1：加表，不改旧读写

- 执行 D1 `0016`；
- 增加 Repository interface；
- 所有现有页面继续读旧数据；
- 新关系入口先写新表，同时保留必要旧快照。

### M2：幂等回填

- 每个账户按 `legacy_person_id` 幂等创建 `relationship_people`；
- 将旧 `relationshipLoops` 转为 case + events；
- 将可明确关联人物的 `lifeEventLoops` 关联到 person；
- 无法确认人物归属的事件保留为 `person_id = null`；
- 不用字符串相似度强行合并人物。

### M3：新表优先、旧表兜底

- Context Builder 优先新表；
- 旧 JSON 只补缺失信息；
- 修改与删除写入 `relationship_revisions`；
- 增加“删除后旧快照不得复活”测试。

### M4：停止旧格式写入

仅在以下验证全部通过后执行：

- 登录用户跨设备一致；
- 游客绑定账户迁移一致；
- 人物 A/B 不串线；
- 删除与人物合并不复活；
- Sites 生产 D1 smoke test 通过；
- 可回滚读取旧 JSON。

本阶段不删除 `account_data.settings_json`。

PostgreSQL 服务端若继续维护，增加语义等价的 `server/database/migrations/010_relationship_engine.sql`；Sites/D1 是当前上线验收主路径。

## 11. Context Builder 与记忆边界

构建关系回答时只加载与当前问题相关的信息：

```text
当前用户的明确偏好
+ 当前人物的已确认关系类型
+ 同一人物近期现实互动
+ 同一人物被用户确认的纠正
+ 当前未完成事件
+ 必要的共享关系事实
```

禁止加载：

- 其他人物的私密事件；
- 已删除事件；
- 未确认的 simulation 作为事实；
- 与当前问题无关的全量聊天历史；
- 对方账户未明确共享的内容；
- 原始截图。

证据优先级：

```text
对方明确共享的自述
> 真实互动结果
> 用户重复现实观察
> 用户单次观察
> 出生象征参考
> simulation 假设
```

## 12. 安全与建议边界

关系策略必须复用并扩展 `lib/safety-boundary.ts`。

需要增加：

- 暴力、胁迫、跟踪、威胁；
- 未成年人和成人恋爱场景；
- 自伤或他伤；
- 财务控制；
- 职场报复与高风险越级；
- 违法或欺骗性操控；
- 冒充他人发送信息。

当安全等级为 `urgent`：

- 不继续优化操控性回复；
- 优先给现实安全行动；
- 不承诺保密或专业诊断；
- 必要时建议联系当地紧急服务或可信现实支持。

普通关系问题中不使用“心理疾病”“回避型人格”等诊断标签替代事实分析。

## 13. 指标与实验

在现有 `product_metric_events` 枚举中增加：

```text

relationship_image_submitted
relationship_clarification_shown
```

指标不得包含聊天正文、姓名、截图哈希或生成回复。

```text

→ 带回现实结果
```

首版产品验收参考：

| 指标 | 目标 |
| --- | ---: |
| 首次提交成功率 | ≥ 95% |
| 首次回答完成率 | ≥ 95% |
| 图片可解析率 | ≥ 85% |
| 必要确认平均次数 | ≤ 1 |
| 回复复制或明确采用率 | ≥ 20% |
| 7 天内同一 TA 再次咨询率 | ≥ 15% |
| 有行动案例的现实反馈率 | ≥ 25% |
| A/B 人物串线 | 0 |
| 原图持久化 | 0 |

这些是 beta 目标，不作为模型效果的确定性承诺。

## 14. 分阶段实施

## R0 — 契约与兼容层

目标：先让底层可扩展，不改变用户界面。

任务：

- 新增 `lib/relationships/types.ts` 与 taxonomy；
- 新增 Repository interface；
- 新增旧 JSON adapter；

验收：

- 当前测试全绿；
- flag 关闭时页面与生产行为不变；
- 新表迁移可重复执行；
- 旧账户无需手工处理即可读取。

## R1 — 常驻纯文本关系工作区

目标：验证“看懂 TA + 怎么回”的即时价值，并确保该入口对所有用户长期可见。

任务：

- 所有用户首屏常驻 `RelationshipWorkspace`；
- 首访用户展示完整说明和三个示例场景；
- 回访用户展示最近案例、最近人物和可切换的 TA；
- Composer 提升到 2,000 字；
- 恋爱三目标分类；
- dating / partner / ex 策略；
- 结构化回答与回复卡；
- 必要时一次轻确认；
- 结果后保存人物；
- 已有 TA 和未完成 case 的连续承接；
- 将今日指引、周度镜像和探索入口放在关系工作区之后；
- 复制与采用指标。

验收：

- 所有用户进入首页第一屏都能直接粘贴聊天或描述关系问题；
- 使用一次后入口不会消失、下沉到页面底部或变成轻量链接；
- 首访用户无需选择人物即可完成；
- 长期用户能从同一入口继续已有 TA，也能切换或新建人物；
- 明确提到男友／女友／前任时不重复询问；
- 回答包含判断、误判边界、建议回复和观察信号；
- 长期用户的今日、周度、人物镜像和待回访内容仍完整保留；
- 现有流式、停止、重试不回归。

## R2 — 图片理解

目标：支持聊天截图，不让图片能力侵入关系数据层。

任务：

- 附件选择、预览、压缩、排序和删除；
- 独立 vision provider；
- 结构化 OCR/视觉提取；
- 说话人必要确认；
- 原图不保存；
- 图片失败后允许转为手动粘贴；
- 视觉金标样本测试。

验收：

- 3 张以内同一对话顺序正确；
- 无法判断左右说话人时只问必要问题；
- 图片正文不进入日志与指标；
- 视觉 provider 失败不影响文本聊天；
- 未配置视觉密钥时前端隐藏上传按钮并保持文本可用。

## R3 — 现实反馈闭环

目标：真实结果改变下一次建议，而不是只记录“顺利/翻车”。

任务：

- case / events / feedback 写入；
- “TA 后来回复了”入口；
- 关联已有 TA；
- Person Mirror 时间线接入；
- Context Builder 读取同一人物反馈；
- 显示“这次为什么和上次建议不同”的自然说明。

验收：

- 用户不需重述背景；
- 上次现实结果能改变策略权重；
- 未确认 simulation 不进入人物事实；
- 删除反馈后不再影响建议；
- 人物 A/B 的反馈完全隔离。

## R4 — 朋友与职场策略

目标：扩展而不改数据层。

顺序：

1. friendship；
2. colleague；
3. manager / report / client。

领导策略必须增加职业风险、证据和表达时机评测。未达到安全评测门槛前不在首页宣传。

## R5 — 家庭策略

家庭最后开发，增加：

- 现实依赖；
- 长期角色固化；
- 未成年人；
- 控制与伤害；
- 边界是否可执行；
- 多年问题不能被一次话术“解决”的限制。

## 18. Definition of Done

PHASE-020 完成必须同时满足：

- 所有用户首页第一屏始终可进入恋爱／关系工作区，使用一次后入口不消失或下沉；

- 关系不确定时只询问真正影响建议的字段；
- 恋爱回答有明确判断和可发送回复；
- 用户可在结果后关联或创建 TA；
- TA 后来的现实回应可直接带回；
- 同一人物的反馈会改变后续建议；

- 原始截图不进入 D1、日志和埋点；
- 长期用户的今日指引、周度镜像、人物轨迹、聊天历史和流式体验完整保留，并位于常驻关系入口之后；
- feature flag 可快速关闭新入口；

## 20. 实施结果

PHASE-020 已按 R0–R5 落地：所有用户首页首屏共用常驻关系工作区，新用户只看到更简洁的引导，长期用户继续保留人物、关系案例、今日指引、周度镜像和历史对话。文字与最多三张聊天截图进入同一关系引擎；截图在浏览器端压缩并去除元数据，服务端只保留内容哈希和处理状态，不保存原图。

统一分类、策略、安全边界、规范化人物／案例／事件／反馈模型及旧数据懒迁移已经接入 Next、Fastify 与 Sites Worker。恋爱、朋友、同事、领导和家庭共享同一契约，通过策略层调整判断重点、可发送回复、现实风险和后续观察信号。现实反馈会绑定 `personId/caseId`，下一次对话优先读取同一人物最近案例，且查询始终受 `owner_user_id` 隔离。

发布保持五个独立回滚开关，默认开启：`RELATIONSHIP_ENGINE_ENABLED`、`NEXT_PUBLIC_RELATIONSHIP_ENTRY_ENABLED`、`VISION_INPUT_ENABLED`、`RELATIONSHIP_NORMALIZED_WRITE_ENABLED`、`RELATIONSHIP_NORMALIZED_READ_ENABLED`。最终验收包含类型检查、关系策略与安全测试、完整回归、静态构建、Worker 合约验证、D1 迁移验证和部署后健康检查。
