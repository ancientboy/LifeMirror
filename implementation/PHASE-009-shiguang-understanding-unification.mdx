# 拾光统一上下文与关系基础改造计划

## 1. 阶段定位

PHASE-009 继续执行，但产品目标已经从“强化 Mirror DNA”调整为：

> **让拾光在聊天、今日拾光、六爻、塔罗、八字、占星、历史记录、周期回顾和关系场景中，都能调用同一份用户授权、可追溯、可纠正的上下文。**

PHASE-009 是 LifeMirror 从“AI + 多种镜像工具”走向“AI-native relationship product”的基础设施阶段。

这一阶段必须让用户真实感受到：

1. 我做过的测算不会莫名消失。
2. 我不需要每次重新解释自己。
3. 拾光知道我正在经历什么，也知道某个人是谁。
4. 历史记录、长期记忆和 Pattern 是不同层级，不会混为一谈。
5. 拾光能基于现实上下文直接给判断，而不是把分析任务重新丢回用户。
6. 在合适时，它能帮助用户把 AI 内部理解转化为真实的人际互动。

本阶段不重新建立第二套 Memory Core，不改成 Multi-Agent，也不重写已经成熟的专业 Tool。

# 2. 产品原则调整

## 2.1 History、Memory、Pattern、Favorite 必须彻底分层

当前“用户是否点击保存”同时影响历史可见性和后续 Memory，这是体验不一致的根源之一。

PHASE-009 明确拆成四层：

### History / 我的记录

**默认自动记录。**

只要一次完整 Tool 结果成功生成，就应该进入用户可查看的历史：

- 六爻完成 → 自动进入历史
- 塔罗完成 → 自动进入历史
- 八字完成 → 更新稳定底图历史
- 占星完成 → 更新稳定底图历史

用户不需要再通过“保存”按钮决定“这次测算以后还能不能找到”。

用户必须可以：

- 查看历史
- 删除单条记录
- 按来源筛选
- 按时间查看
- 从历史记录继续和拾光聊
- 关联到某个人/某段关系
- 标记重要

结果页面改为显示：

> ✓ 已自动记录

原“保存”按钮应逐步替换为：

- 标记重要
- 关联到某人
- 删除
- 继续聊

### Memory / 拾光长期记得

History 自动记录 **不等于** 自动进入长期 Memory。

Memory 只接受：

- 用户明确要求记住的事实
- 用户主动确认的重要现实事件
- 用户明确表达的沟通偏好
- 符合授权和质量门槛的长期线索

例如：

```text
History：今天抽到了“隐者”
≠
Memory：用户是一个内向的人
```

### Pattern / 长期线索

Pattern 的门槛高于 Memory。

只有多条独立、现实可追溯的 evidence 才能形成行为或长期主题 Pattern。

Symbolic Tool 结果不能独立制造固定人格。

### Favorite / 重要

Favorite 是用户主动行为，而不是“是否保存历史”。

可用于：

- 标记重要
- 以后提醒我
- 这件事还没结束
- 关联到某个人

推荐数据流：

```text
Tool Result / Conversation
          ↓
       History（默认）
          ↓
是否满足长期记忆条件？
          ↓
       Memory
          ↓
多条独立现实证据？
          ↓
       Pattern
```

---

## 2.2 Bazi / Astrology 不应产生重复历史垃圾

六爻和 Tarot 是一次性事件型结果，每次完整结果可以产生一条 History。

Bazi / Astrology 属于稳定底图，应继续利用现有 `profileKey` / natal cache 设计：

```text
birth profile
    ↓
已有相同 stable reference？
    ↓
复用 / 更新访问时间
```

只有以下情况生成新版本：

- 出生资料发生修改
- 用户明确更正资料
- 算法版本升级并需要重新计算
- 用户明确创建新版本

本命盘不能因为重复打开而制造大量重复 History 或 Pattern evidence。

---

## 2.3 Mirror DNA 降级为后台能力

Pattern Memory、confidence、evidence、user correction 继续保留。

前台不再把以下内容作为核心价值：

- “Mirror DNA 正在形成”
- “还需要更多记录”
- “这是第一次观察”
- “再记录几次就会更了解你”
- 系统建模进度

这些表达技术上谨慎，但用户价值低。

“我的”应该替换成真正有信息量的内容：

### 最近的我

- 最近发生过什么
- 最近反复在意什么

### 还没结束的事

- 上次正在等的结果
- 尚未解决的关系问题

### 拾光记得

- 明确事实
- 沟通偏好
- 用户自己确认的重要背景

### 最近的变化

- 有 evidence 支持的阶段变化

### 人物

- 用户人生中正在被反复提到的人
- 每个人独立的关系上下文

### 我的底图

- 八字 / 星盘 stable reference

# 4. 当前确认的主要断点

## A. Tool 结果历史依赖用户手动保存

当前部分 Tool 结果需要用户主动点击保存后才能进入本地 Mirror History / 后续 Memory。

直接结果是：

> 用户明明刚做过一次测算，但“我的镜像”中可能看不到。

这是 P0 产品一致性问题。

## B. Server Memory 仍明显以六爻 Reflection Event 为中心

当前 `MemorySourceEvent` 直接依赖六爻相关的：

- `hexagram_result`
- `knowledge_context`
- `reflection`

问题不是“没有 Memory”，而是 **Memory ingestion source 不统一**。

## C. 普通拾光聊天仍使用客户端 Memory

`ShiguangChat.tsx` 当前主要通过 localStorage facts / history 和 client relevance 组装 memory。

登录用户没有统一使用 server personal context。

## D. 登录用户“我的镜像”仍没有真正消费 Server Pattern

`PersonalMirrorDashboard.tsx` 登录后仍主要读取 local history，并在前端运行 `deriveDnaPatterns()`。

因此存在：

```text
后台真实 Pattern Memory
≠
前端自己计算的 Mirror DNA
```

## E. Tarot / Bazi / Astrology History 与 Server Memory 没有统一

当前部分结果保存到本地 history，但不会自然进入 server Pattern pipeline。

## F. Chat / Daily / Reflection / Review 使用不同 Context 规则

缺少统一 Personal / Relationship Context contract。

## G. Runtime trace 与真实生命周期未完全一致

部分 Tool direct execute 后再手工构造 trace；persistence trace 与真实保存动作可能不一致。

## H. Account / API 存储边界需要明确

Fastify/Postgres 与 `.openai/drizzle` / Sites runtime 路径并存，需要明确生产 source of truth。

# 5. P0 — 先解决数据连续性与统一上下文

## P0-1. 所有完整 Tool Result 默认自动进入 History

这是 PHASE-009 新增的最高优先级任务。

### 六爻 / Tarot

每一次完整结果成功生成后：

- 自动生成 History record
- 不要求用户点击“保存”
- 保留 result source / question / generatedAt / structured payload / reflection
- 支持删除
- 支持继续聊天
- 支持关联 Person / Relationship

### Bazi / Astrology

- stable reference 自动记录
- 使用 `profileKey` / version 做去重
- 重复打开不新增独立记录

### Guest

- 自动进入 local history
- 允许删除
- 登录迁移时必须 dedup

### Authenticated

- 自动进入 account/server history
- 跨设备可见

### UI

原：

> 保存

改为：

> ✓ 已自动记录

并提供：

- 标记重要
- 关联到某人
- 删除

### 验收

用户完成任何一次六爻/塔罗完整结果后，立即进入“我的 → 最近记录”，不需要额外点击。

不永久保存全部聊天。

- 用户明确说“记住……”

- 用户明确表达的沟通偏好

History 自动记录以后，再由 source adapter 决定哪些信息可以进入 Memory。

规则：

- stable reference 不参与重复 signal count

# 6. P1 — Open Loop + People + Relationship Context

## P1-1. 增加 Open Loop

重要现实事件支持：

- `open`
- `resolved`
- `unknown`

只能根据用户反馈或明确现实事件更新。

示例：

> “上次你还在等那个合作结果，后来怎么样了？”

---

## P1-2. 增加 Person 数据契约

用户可以创建一个现实中已经存在的人，即使对方尚未注册 LifeMirror。

第一版字段建议：

```ts
type Person = {
  id: string;
  ownerUserId: string;
  displayName: string;
  relationshipType?: string;
  birthProfile?: ...;
  userDescription?: string;
  userObservedTraits?: ...;
  createdAt: string;
};
```

可以输入：

- 昵称
- 与我的关系
- 生日信息（可选）
- 用户认为 TA 的性格特点
- 沟通方式
- 最近发生过什么
- “TA 在你心里是什么样的人？”

### 最重要的 provenance 原则

用户描述：

> “Alex 很自私。”

不能存成：

```text
Alex.personality = selfish
```

只能存成：

```text
source = current_user
observation = “用户认为 Alex 最近在这段关系里比较只顾自己”
```

**用户眼中的 TA ≠ 真实 TA。**

---

## P1-3. Relationship Context

一个 Person 可以关联一个或多个 Relationship Context。

建议 contract：

```ts
type RelationshipContext = {
  id: string;
  ownerUserId: string;
  personId: string;
  relationshipType: string;
  userPerspective: ...;
  events: ...;
  openLoops: ...;
  sharedFacts?: ...;
  sharedInteractions?: ...;
};
```

优先使用：

1. 双方明确陈述
2. 已记录现实事件
3. 用户 perspective
4. stable birth reference
5. symbolic interpretation

禁止通过出生资料或用户单方描述直接断言对方心理状态。

# 7. P1 — Relationship Sandbox / 关系沙盒

这是从 AI 理解走向真实社交之前的关键中间产品。

用户可以创建一个“现实中的 TA 的模拟关系对象”，在对方尚未注册时获得立即价值。

它不是 Character.AI 风格的虚拟朋友，也不是“真实 TA 的数字分身”。

定义：

> **基于用户目前知道和描述的信息，建立一个可纠正的 Relationship Model，用于理解关系和练习现实沟通。**

## 7.1 关系演练模式

### 练习怎么说

用户：

> “我想告诉 Alex 我不喜欢他忽冷忽热，但不知道怎么说。”

拾光：

- 帮用户组织表达
- 可以进行多轮 rehearsal
- 关键节点暂停并给用户判断

### 模拟可能回应

系统必须明确：

> “按照你目前对 Alex 的描述，一种可能的反应是……”

而不是：

> “Alex 会这样想。”

支持给出 2–3 种合理反应路径，避免单一预测制造错觉。

### 换位看看

帮助用户评估：

- 这句话从对方可能视角听起来如何
- 哪部分容易被误解
- 哪部分表达了真实需求

### 困难谈话

不仅限恋爱：

- 和老板谈加薪
- 和父母谈边界
- 和室友谈冲突
- 和朋友谈疏远
- 和伴侣谈回应节奏

---

## 7.2 Birth / Astrology / Bazi 在关系沙盒中的作用

生日信息可以作为额外 perspective，但现实互动永远优先。

推荐顺序：

```text
真实互动历史
+ 用户明确描述
+ 对方本人未来提供的信息
+ 双方 stable birth reference
+ symbolic perspective
```

禁止：

```text
“Alex 是天蝎座，所以他一定……”
```

可以：

> “从你记录的现实互动看，核心首先是回应节奏；出生底图只能作为补充视角。”

# 8. P1 理解质量升级

## 8.1 Memory Retrieval Ranking

第一阶段不必直接上 vector DB。

Ranking 考虑：

- relevance
- recency
- explicit fact priority
- user correction
- pattern confidence
- source diversity
- open loop priority
- person / relationship match

## 8.2 Pattern Engine 从数量升级为 evidence quality

至少加入：

- 时间跨度
- 来源多样性
- 用户确认/纠正
- 冲突证据
- 最近是否仍成立

## 8.3 Communication Preference

用户明确表达：

- 喜欢直接结论
- 不喜欢鸡汤
- 不喜欢连续追问
- 希望解释深入

应成为高权重 Fact。

## 8.4 Daily Guidance 接统一 Context

保留：

```text
本命底图
+ 今日变量
+ 当前现实
```

再加入：

- 最相关 open loop
- relevant person / relationship
- relevant Pattern

用户界面不解释后台机制。

# 10. P2 — 从模拟关系走向真实关系

## P2-1. Simulated Person → Real User Invite

用户一开始可以单方面创建 Alex。

使用一段时间以后出现：

> **想知道真实的 TA 怎么看？**

允许邀请 Alex 加入。

但不能把用户创建的模拟资料直接声明为真实 Alex 的资料。

必须拆成三层：

```text
用户对 Alex 的理解
+
Alex 自己提供的信息
+
双方共享的 Relationship Events
```

---

## P2-2. Claim / Link 机制

真实 TA 注册后：

- 可以 claim / link 到原来的 Person object
- 用户单方 observation 保留 provenance
- TA 自己的信息独立保存
- 双方共享信息必须双方授权

系统必须能容纳：

```text
Leo perspective
≠
Alex perspective
```

这不是数据冲突，而是 Relationship Context 的核心价值。

---

## P2-3. 第一版 Social Action：把一个问题发给 TA

不要先做 Feed。

例如：

> **想听听 TA 怎么看？**

发送：

> “你忙的时候没及时回复，更希望对方继续找你，还是等你主动？”

对方回答后只总结真实答案差异。

不分享完整 AI 对话。

---

## P2-4. 分享卡升级成关系互动

三类：

1. 表达自己
2. 问一个认识的人
3. Relationship Card

核心指标：

> 分享后是否得到真实回应。

---

## P2-5. 暂不做陌生人匹配

0.9 不做：

- 灵魂好友匹配
- Mirror DNA 匹配
- 公共 Feed
- 热门广场
- 陌生人聊天大厅

先验证：

```text
个人问题
→ 关系沙盒
→ 现实沟通
→ 对方回应
→ 回来告诉拾光
→ 最终邀请真人
```

# 11. Runtime / Engineering 一致性

## 11.1 ToolRegistry 契约

明确 direct deterministic engine 与 ToolRegistry / trace 的职责关系。

## 11.2 Persistence Trace

Runtime trace 应真实反映：

- History 是否自动记录
- Memory 是否写入
- Tool 是否成功
- Reflection 是否成功

## 11.3 History 去重

必须有 deterministic dedup key，避免：

- result 页面 rerender 重复保存
- 网络 retry 重复保存
- 登录迁移重复保存
- stable natal reference 重复保存

建议 key 至少包含：

```text
user/client
source kind
calculation/result id
version
```

## 11.4 Memory / Context Observability

内部 trace 增加：

- retrieved history IDs
- memory IDs
- selected source kinds
- ranking reason
- filtered reason
- person/relationship match
- context token size

不在用户 UI 暴露完整 prompt。

# 12. 明确不做

## 不让用户手动决定“这次测算是否存在”

History 默认自动。

## 不把自动 History 等同于自动人格 Memory

# 14. P0 验收标准

## Case 1 — 自动历史

用户完成一次六爻或 Tarot 后，不点击任何“保存”按钮，进入“我的 → 最近记录”仍能看到刚才的完整结果。

## Case 2 — 删除历史

用户删除一条 History 后，该记录不再展示；如果对应长期 Memory 也需要删除，系统明确告诉用户删除范围，不偷偷保留不可见副本。

## Case 3 — Stable Natal 去重

同一 birth profile 连续打开三次八字/星盘，不产生三条重复 stable record。

## Case 4 — History 不等于人格

用户抽到一次“隐者”，历史里存在这次记录，但长期 Pattern 不会自动出现“用户内向”。

## Case 5 — 跨设备连续性

设备 A 产生历史并登录；设备 B 能看到同一条记录。

## Case 6 — 用户纠正优先

用户纠正 Memory 后，下一次回答使用纠正版本。

## Case 7 — 删除即停止使用

hidden/deleted Memory 不再进入 Context。

## Case 8 — Dashboard 与 Server 一致

登录用户“我的”显示的 Pattern 与 server Memory 一致。

## Case 9 — 无意义“正在形成”退出核心 UI

即使只有一条记录，也展示真实记录和现实内容，而不是只展示模型状态。

# 15. Relationship Sandbox 验收标准

## Case A — 创建现实中的 TA

用户可以创建一个尚未注册 LifeMirror 的 Alex，并输入自己知道的信息。

## Case B — provenance

用户说“Alex 很冷漠”，系统只保存为“用户对 Alex 的观察”，不得保存为 Alex 的客观人格事实。

## Case C — rehearsal

用户可以针对 Alex 进行一次困难谈话演练。

系统输出必须显式基于“用户目前提供的信息”，不得声称真实 Alex 一定会这样回应。

## Case D — 多种可能回应

系统可以提供多种可能的反应路径，而不是单一预测对方心理。

## Case E — 邀请真人后不覆盖原 perspective

真实 Alex 加入后：

- Leo perspective 保留
- Alex self-reported data 独立
- shared facts 独立

三者不能混写。

# 16. 关键成功指标

PHASE-009 不再以 Mirror DNA 浏览次数作为关键指标。

优先观察：

1. Tool 完成后 History 找回率是否接近 100%。
2. 用户是否经常从历史记录继续聊天。
3. 用户是否在不使用 Tool 时主动找拾光。
4. 用户是否回来告诉拾光“后来发生了什么”。
5. Open Loop 是否出现真实后续更新。
6. Relationship Sandbox 是否帮助用户产生现实沟通。
7. 分享给真实关系对象后是否得到回应。
8. 模拟 Person 转成真实邀请的比例。
9. 用户纠正 Memory 后是否继续使用该能力。

其中最重要的长期行为仍然是：

> **用户回来告诉拾光“后来发生了什么”。**

关系方向新增的关键增长行为是：

> **AI 中的关系理解是否最终产生了一次真实的人际互动。**

LifeMirror 的长期差异化不应该是：

> “我们建立了一个更复杂的 Mirror DNA。”
