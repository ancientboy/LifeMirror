# 拾光统一上下文与关系基础改造计划

## 1. 阶段定位

PHASE-009 继续执行，但产品目标调整。

这一阶段不再以“把 Mirror DNA 做得更完整”作为主要目标，也不把“人生模型正在形成”作为用户价值。

新的目标是：

> **让拾光在聊天、今日拾光、六爻、塔罗、八字、占星、周期回顾和关系场景中，都能调用同一份用户授权、可追溯、可纠正的上下文。**

PHASE-009 是 LifeMirror 从“AI + 多种镜像工具”走向“AI-native relationship product”的基础设施阶段。

核心用户价值不是让用户看到系统如何建模，而是让用户真实感受到：

1. 拾光记得我正在经历什么。
2. 我不需要每次从头解释。
3. 拾光知道某个人是谁、这段关系发生过什么。
4. 它能基于现实上下文直接给出判断，而不是把分析任务重新丢给用户。
5. 当合适时，它能帮助用户把 AI 内部理解转化为真实的人际互动。

---

# 2. 产品方向调整

## 2.1 Mirror DNA 降级为后台能力

当前 Pattern Memory、confidence、evidence、user correction 仍然保留。

但前台不再把以下内容当作核心体验：

- “Mirror DNA 正在形成”
- “还需要更多记录”
- “这是第一次观察”
- “再记录几次就会更了解你”
- 以系统置信度、建模进度作为主要反馈

这些内容可以作为内部安全边界，但对用户没有足够直接价值。

### 前台替换为四类真正有信息量的内容

#### 最近的你

只展示当前有证据支持的事实或主题，例如：

- 最近两周你多次提到工作方向。
- 这段关系最近又出现了回应节奏的问题。
- 你最近反复在权衡“继续投入”还是“先停一下”。

#### 还没结束的事

例如：

- 上次你说正在等合作方回复。后来有消息了吗？
- 你之前决定先不主动联系 TA，这件事现在有变化吗？

#### 拾光记得

只展示用户明确授权或高可信的事实/偏好，例如：

- 你希望别人直接给判断，不喜欢反问式建议。
- 你目前正在准备换工作。

#### 最近有什么变化

基于多条事件和时间变化，而不是固定人格标签。

例如：

- 以前你更在意“要不要做”，最近你更在意“值不值得继续投入”。

# 3. 当前代码事实基线

本计划基于当前 `main` 分支实际实现。

## 已经存在并应保留

### Server Memory System

已有：

- `server/memory/extractor.ts`
- `server/memory/processor.ts`
- `server/memory/reflection-context.ts`
- `server/routes/memories.ts`
- `server/database/migrations/003_memory_system.sql`

已有能力：

- Event Memory
- Reflection Memory
- Pattern Memory
- evidence links
- processing runs
- pattern suppression
- 用户查看、纠正、隐藏、删除和导出

因此禁止重新建立第二套 Memory Core。

### Runtime / Harness

已有：

- `server/runtime/runtime.ts`
- `server/runtime/tool-registry.ts`
- `server/llm/shiguang-runtime.ts`

已有 mode、memory、knowledge、tool、reflection、evaluation、trace 等基础。

因此保持：

```text
一个拾光人格
+ 一个 Harness / Runtime
+ 多个专业 Tools
+ Memory / Knowledge / Evaluation
```

不改成 Multi-Agent。

### 专业工具

六爻、塔罗、八字、占星均已有结构化能力。

本阶段重点是统一 Context 和 Memory，不重写专业引擎。

### Review

Weekly / Monthly Review 已实现，并已有 evidence、confidence、preference、cooldown。

本阶段只需要让 Review 消费统一后的多来源 Memory，不重新开发 Review Engine。

# 4. 当前确认的主要断点

## A. Server Memory 仍明显以六爻 Reflection Event 为中心

当前 `MemorySourceEvent` 直接依赖：

- `hexagram_result`
- `knowledge_context`
- `reflection`

`processReflectionEvent()` 从 `reflection_events` 进入 Memory pipeline。

因此当前问题不是“没有 Memory”，而是 **Memory ingestion source 不统一**。

## B. 普通拾光聊天仍使用客户端 Memory

`ShiguangChat.tsx` 当前主要通过：

- `lib/shiguang-memory.ts`
- localStorage saved facts
- local mirror history
- client relevance

组装 memory 后请求 `/api/shiguang`。

登录用户没有统一使用已有 `/api/v1/memories/context` 作为长期上下文来源。

## C. 登录用户“我的镜像”仍没有真正消费 Server Pattern

`PersonalMirrorDashboard.tsx` 登录后仍主要读取 local history，并在前端运行 `deriveDnaPatterns()`。

因此存在：

```text
后台真实 Pattern Memory
≠
前端自己计算的 Mirror DNA
```

这必须统一。

## D. Tarot / Bazi / Astrology 保存主要落到本地 Mirror History

`MirrorSaveButton.tsx` 当前保存 `tarot | bazi | astrology` 到本地 history。

登录后的 account snapshot 同步不等于进入 server Pattern pipeline。

## E. Chat / Daily / Reflection / Review 使用不同 Context 规则

当前分别存在：

- client chat memory retrieval
- daily recent history
- server reflection context
- review memory queries

缺少统一 Personal Context contract。

## F. Runtime trace 与真实生命周期未完全一致

部分工具 direct execute 后再手工构造 tool trace；`runMirrorRuntime()` 中 persistence stage 仍可能显示 skipped，而 route 后续真实执行保存。

需要统一运行契约。

## G. Account / API 存储边界需要明确

当前仓库中 Fastify/Postgres 和 `.openai/drizzle`/Sites runtime 路径并存。

必须明确：

- 哪套 API 负责哪些功能
- identity 是否一一对应
- account snapshot 与 server Memory 的关系
- social API 的生产实现边界

# 5. P0 — 统一拾光上下文主链

## P0-1. 建立通用 Memory Ingestion Contract

在现有 `server/memory` 上扩展，不重建数据库。

支持 source kind：

- `liuyao`
- `tarot`
- `bazi`
- `astrology`
- `conversation`

每种 source 必须明确区分：

1. user-authored reality
2. symbolic/professional facts
3. model interpretation

规则：

> LLM interpretation 和 symbolic result 都不得自动升级为用户现实事实或固定人格。

## P0-2. 登录用户聊天改读 Server Memory

Authenticated：

- 优先使用 server personal context。
- hidden/deleted/suppressed Memory 不得进入 prompt。

Guest：

- 保留现有 local fallback。

Temporary mode：

- 不读取、不写入长期 Memory。

## P0-3. 建立 Conversation Memory Write Gate

不永久保存所有聊天内容。

第一版只允许：

- 用户明确说“记住……”的事实。
- 用户主动确认保存的重要现实事件。
- 用户明确表达的沟通偏好。

例如：

> “不要一直反问我，直接告诉我判断。”

可以保存为 communication preference。

普通寒暄不进入长期 Pattern。

## P0-4. Tarot / Bazi / Astrology 接入 Server Memory

登录用户保存 Mirror 后创建统一 source record。

规则：

- Tarot 是当次 symbolic evidence，不是人格事实。
- Bazi/Astrology 是 stable reference，不因重复打开而形成多条独立 Pattern evidence。
- Liuyao 是一次具体事件/问题的 symbolic evidence。

## P0-5. PersonalMirrorDashboard 改读 Server Memory

Authenticated：

- 读取 `/api/v1/memories/summary` / `/api/v1/memories`。
- 不再依赖前端 regex 作为权威 Pattern 来源。

Guest：

- 保留本地 fallback。

## P0-6. 删除无证据的人格补全

禁止从“一个主题出现多次”自动推出：

- 你很谨慎
- 你会过度分析
- 你习惯先想清楚再表达
- 你是什么类型的人

只有现实事件、多条用户事实或明确确认才能形成行为 Pattern。

## P0-7. 建立统一 Personal Context Builder

建议新增：

`server/memory/context-builder.ts`

统一 contract：

```ts
type PersonalContext = {
  explicitFacts: ...;
  relevantEvents: ...;
  relevantPatterns: ...;
  stableReferences: ...;
  openLoops: ...;
  people: ...;
  currentContext: ...;
  provenance: ...;
};
```

不同 mode 根据授权裁剪：

- chat
- mirror_result
- daily_guidance
- review
- relationship

## P0-8. 明确 Account / API Source of Truth

形成明确 production boundary 文档与 integration tests。

# 6. P1 — 从“认识用户”升级到“理解用户正在经历的人和事”

## P1-1. 增加 Open Loop 概念

重要现实事件增加轻量状态：

- `open`
- `resolved`
- `unknown`

状态只能来自用户反馈或明确事件更新，不能由 LLM 自己宣布解决。

价值：

```text
“上次你在等那个合作结果，后来怎么样了？”
```

而不是泛泛说：

```text
“我记得你之前也有类似困扰。”
```

## P1-2. 增加 People / Relationship Context 的数据契约

先支持 context contract，不急着一次建完全部数据库。

目标实体：

```text
Person
Relationship
Relationship Event
Open Loop
Shared Interaction
```

示例：

```text
Person: Alex
Relationship: 用户描述为暧昧对象
Events:
- 两天没有回复
- 用户决定暂时不主动
Open loop:
- 关系定义仍未确认
```

禁止自动推断：

- Alex 是回避型人格
- Alex 一定不在乎用户
- 对方心理状态

除非对方本人提供或现实事件明确证明。

## P1-3. Memory Retrieval Ranking 升级

第一阶段不必直接上 vector DB。

Ranking 至少考虑：

- relevance
- recency
- explicit fact priority
- user correction
- pattern confidence
- source diversity
- open loop priority
- person / relationship match

## P1-4. Pattern Engine 从数量权重升级为证据质量

在当前至少两条独立 evidence 规则基础上增加：

- 时间跨度
- 来源多样性
- 用户确认/纠正
- 冲突证据
- 最近是否仍成立

Pattern 继续作为后台能力，不作为前台“人格测评结果”。

## P1-5. Communication Preference 成为高权重 Fact

用户明确表达的交互偏好应该影响拾光长期表达方式。

例如：

- 喜欢直接结论
- 不喜欢鸡汤
- 不喜欢连续追问
- 希望解释深入一些

## P1-6. Daily Guidance 接入统一 Context

保留正确基础：

```text
本命底图
+ 今日变量
+ 当前现实
```

升级后加入：

- 当前最相关 open loop
- 相关长期 Pattern
- 当前 relationship context

但用户界面不展示后台机制。

## P1-7. ToolRegistry / Runtime 契约统一

明确 direct deterministic engine 和 ToolRegistry trace 的关系，不保留模糊双轨。

## P1-8. Persistence Trace 与真实保存结果一致

Runtime trace 应能真实回答：

- 是否读取 Memory
- 是否调用 Tool
- 是否生成 Reflection
- 是否真正保存

## P1-9. `question-routing.ts` 保留为 UI/fallback

不要把 regex router 升级为 Harness 核心决策器。

# 7. P1 产品展示重构

## 7.1 首页：拾光成为第一入口

首页目标从“选择工具”转为：

> **今天怎么了？**

优先展示：

1. 今日拾光的一句话
2. 上次还没结束的事
3. 当前聊天入口
4. 必要时由拾光自然建议工具

工具入口不删除，但降级到 Explore。

## 7.2 “我的镜像”重构

不再以 Mirror DNA 作为中心。

建议页面结构：

### 最近的我

现在真正反复出现的主题。

### 还没结束的事

open loops。

### 拾光记得

explicit facts / preferences。

### 最近的变化

evidence-backed changes。

### 我的底图

Bazi / Astrology stable reference。

### 记录与控制

进入 MemoryControls 查看、纠正、隐藏、删除、导出。

## 7.3 主导航建议

逐步向以下结构靠拢：

```text
拾光
我的
关系
探索
```

其中：

- 拾光：日常聊天 / 今日 / open loops
- 我的：个人上下文与近期变化
- 关系：未来 Me × You / private relationships
- 探索：六爻 / 塔罗 / 八字 / 星盘

# 8. P2 — Relationship Foundation

本阶段只建立“已有关系”的社交入口，不做公开 Feed 和陌生人匹配。

## P2-1. 第一版「我和 TA」

用户可以围绕一个现实中的人建立私密 Relationship Context。

场景优先：

- 暧昧对象
- 伴侣
- 好朋友
- 室友
- 同事
- 前任

核心不是 compatibility score，而是：

> 这段关系发生过什么、双方对什么有不同理解、下一步怎么表达。

## P2-2. 第一版 Social Action：把一个问题发给 TA

不要先做完整好友 Feed。

例如拾光分析后提供：

> **想听听 TA 怎么看？**

生成一个轻量问题：

> “你忙的时候没及时回复，更希望对方继续找你，还是等你主动？”

对方回答后，LifeMirror 只总结双方真实答案差异。

这比分享完整 AI 聊天记录更自然，也更保护隐私。

## P2-3. 分享卡从“内容传播”升级为“关系互动”

三类：

1. 表达自己
2. 问一个认识的人
3. Relationship Card

目标指标不是分享次数，而是：

> 分享后是否产生真实回应。

## P2-4. 暂不做陌生人匹配

以下功能不属于 0.9 优先级：

- 灵魂好友匹配
- Mirror DNA 匹配
- 公共动态 Feed
- 热门广场
- 陌生人聊天大厅

未来若验证 stranger social，再以“正在经历相似人生阶段的人”作为候选方向，而不是人格相似度。

# 11. P0 验收标准

## Case 1 — 跨设备连续性

设备 A 保存重要 Mirror；设备 B 登录后聊到相关问题，拾光能自然使用同一份 server Memory。

## Case 2 — 用户纠正优先

用户纠正某条 Memory/Pattern 后，下一次相关回答使用纠正版本。

## Case 3 — 删除即停止使用

hidden/deleted Memory 不再进入任何 Context。

## Case 4 — 多工具连续性

用户先用塔罗留下关系问题，之后普通聊天可以自然继续这件事，但不会把牌面当成现实事实。

## Case 5 — Dashboard 与 Server 一致

登录用户“我的镜像”显示的长期线索与 server Pattern 一致，不再由前端另算一套答案。

## Case 6 — 无意义“正在形成”内容退出核心页面

用户不需要等待 Mirror DNA 达到某个进度才获得价值。

即使只有一条真实记录，也应该能够看到：

- 最近发生的事
- 拾光记住的明确事实
- 当前未结束的问题

## Case 7 — Context 能识别人和关系

同一个人名/关系在后续聊天中可以被正确关联到已有事件，但不会凭空推断对方人格或心理状态。

# 12. 关键成功指标

PHASE-009 完成后，不只看功能完成度。

优先观察：

1. 用户是否在不使用工具的情况下主动和拾光继续聊天。
2. 用户是否主动追问“你还记得我之前说的……”。
3. 同一个 open loop 是否出现后续更新。
4. Mirror/Chat 后是否产生现实行动。
5. 分享给现实中的人后是否得到回应。
6. 用户纠正 Memory 后是否继续使用该能力。

其中最重要的行为信号是：

> **用户回来告诉拾光“后来发生了什么”。**

这比 Mirror DNA 浏览次数更能证明长期陪伴和关系产品价值。

# 13. 最终技术路线

```text
User-authored reality / explicit preferences / saved Mirror
                         ↓
                Unified Memory Ingestion
                         ↓
        Event / Reflection / Pattern / Open Loop
                         ↓
             People / Relationship Context
                         ↓
               Personal Context Builder
                         ↓
                 Shiguang Harness
              ↙          ↓          ↘
           Tools      Knowledge    Research
              ↘          ↓          ↙
                Evidence / Evaluation
                         ↓
                    Shiguang reply
                         ↓
           correction / outcome / new event
                         ↓
                   update Context
                         ↓
                 optional real-world social action
```

LifeMirror 的长期差异化不应该是：

> “我们建立了一个更复杂的用户模型。”

而应该是：

> **拾光知道我正在经历什么，所以它更懂我为什么在这段关系里纠结，并且能帮助我把想法带回真实的人际关系。**
